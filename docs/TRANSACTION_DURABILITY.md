# Transaction coordination and recovery

Clustered transaction operations run on the elected controller. Network requests to another broker are routed to it; the controller sends authenticated TLS commands to the assigned data-partition leaders. Use `InitProducerId`, `BeginTx`/`AddPartitionsToTxn`, transactional produce with the returned producer ID/epoch, then `EndTxn`. The epoch-less legacy `CommitTx`/`AbortTx` commands reject initialized transactional producers; they cannot bypass producer fencing.

The controller records transaction state, partition ranges, prepare decisions and completion in the replicated `__cluster_metadata` log. State changes and producer epochs take effect only after durable controller-majority acknowledgement. Followers apply committed metadata, including an empty push advancing the watermark. Snapshot recovery includes transaction decisions, their revisions, producer allocations and read-committed pins. Snapshot writes use atomic replacement and fsync; malformed snapshots/state records fail validation.

Before appending a transactional batch, every assigned replica must durably apply its first-offset pin. This prevents a replica whose metadata is behind from exposing uncommitted data. It also means an unavailable assigned replica can prevent a transaction write, even when a data majority remains available. After the pin barrier, data and control markers require a durable replica majority and the configured `min.insync.replicas` floor before acknowledgement. A follower cannot advertise its replication offset before syncing it.

Completion commits the prepare decision first, writes markers on each partition's current leader, waits for acknowledgements, and then commits the terminal decision. Abort ranges persist on local replicas before their read-committed pins are released. Lost replies and interrupted marker writes can be retried; a prepared commit cannot switch to abort. Marker retries may append duplicate control markers. Completed decisions make repeated `EndTxn` calls idempotent while that transaction remains the latest use of its transactional ID.

A new controller restores the committed state and periodically retries prepared decisions. Expired ongoing transactions are aborted; prepared commits are completed as commits. A failed or timed-out metadata proposal fences further transaction mutations on that coordinator until restart/recovery, and an unresolved metadata tail blocks new transaction proposals. Errors are uncertain outcomes: retry the same decision after recovery rather than assuming it failed everywhere.

Rust callers in a cluster use `begin_transaction_coordinated`, `add_partitions_coordinated`, `init_producer_id_coordinated`, `end_transaction_coordinated` and `produce_batch`. The synchronous transaction APIs remain available for standalone embedded use and reject clustered mutations. SASL/ACL checks remain active for client traffic; forwarding does not delegate a SASL principal, so authenticated clients should connect to the controller.

Upgrade every broker before using this protocol: it adds transaction metadata type `0x0D` and broker command/response frame types 9/10. TLS commands require a pinned controller identity, matching cluster/term, an assigned partition and the expected committed transaction revision. Plaintext operation is available only through the explicit insecure development setting documented in PEER_SECURITY.md.

Validation covers three brokers with TLS, remote partition leaders, commit/abort, read-committed pins, controller handover, restart/snapshot recovery, storage failures, insufficient marker quorum, missing replica pins and follower client routing. Controller handover tests explicitly grant an election majority to isolate transaction recovery. These checks do not establish correctness under every network partition, divergent-log reconciliation or physical power-loss scenario; the transaction protocol relies on the broker's existing controller consensus and partition-leadership machinery.
